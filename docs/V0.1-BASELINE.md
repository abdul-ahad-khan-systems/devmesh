# DevMesh v0.1 Baseline — Closeout / v0.2 Boundary

**Status:** DevMesh v0.1 baseline. Six identified load-bearing defects have been
fixed and committed. Remaining findings are explicitly documented technical
debt or test-quality issues — not resolved, not hidden.

This document is the frozen reference point before any v0.2 (ECC/gstack/CCG-
influenced) work begins. It exists so v0.2 design decisions are made against
documented reality, not memory or assumption.

---

## 1. What v0.1 Actually Guarantees

- The execution/tool gate blocks the destructive/environment-probing command
  patterns it targets, including two previously-exploitable bypasses (doubled
  whitespace, subshell repository-escape) that are now closed.
- Model/provider failover actually fires on real transport-level failures,
  not only on well-formed HTTP error responses.
- Repository evidence computed during a mission is persisted onto mission
  state, not silently discarded.
- Model routing — both the `FRELLM_MODEL` override and the no-capable-
  candidate fallback path — respects each role's declared capability
  requirements (`tools`, `tool_choice`, `reasoning_effort`) rather than
  routing on existence/availability alone.
- The full 19-file test suite executes in every run (`npm test`,
  `npm run test:integration`, `npm run test:all`); no test file is silently
  skipped by a short-circuiting `&&` chain, and exit codes accurately
  reflect the aggregate result.
- Zero test files in the suite require a live external service — every
  network-looking test mocks `fetch` entirely.

None of this claims DevMesh is complete, production-hardened, or free of
defects beyond what's listed below. It claims exactly what was verified by
execution, no more.

## 4. Architectural Boundaries

### DevMesh ↔ FreeLLMAPI

DevMesh and FreeLLMAPI are treated as separate systems everywhere else in
this codebase — DevMesh calls FreeLLMAPI only over HTTP (`/v1/models`,
`/v1/chat/completions`) in every other code path. Item #15 is the one
exception: when `FRELLM_API_KEY` is not set in the environment, DevMesh's
bootstrap falls back to importing and executing FreeLLMAPI's own database
module directly (`import(pathToFileURL(dbModule).href)`), reaching into
`~/freellmapi/server/src/db/index.ts` by assumed relative path and assumed
export shape.

This is real, load-bearing cross-project coupling, not a stylistic
inconsistency. If FreeLLMAPI's internal file layout or exports change,
DevMesh's bootstrap breaks with only a generic wrapped error. It is not
currently a security defect (no user-controlled input reaches this path),
but it is an architectural violation of the "DevMesh only talks to
FreeLLMAPI over HTTP" boundary that holds everywhere else.

**This should not be resolved as incidental v0.2 cleanup.** It needs its own
explicit decision: either (a) require `FRELLM_API_KEY` to always be set
externally and remove the fallback entirely, or (b) keep the fallback but
make it an intentional, documented integration point rather than an
undocumented import-and-execute path.

### DevMesh ↔ Standard Connector

Unrelated codebase, unrelated audit, tracked separately. No architectural
entanglement currently exists between the two.

## 5. What Must NOT Change During v0.2 Without a New Architectural Decision

- The execution/tool gate's denylist approach and its two closed bypasses
  (items #1, #2) — any v0.2 workflow/strategy layer must route shell
  execution through the existing gate, not around it.
- The capability-aware routing contract established by fixes #5/#6 — any
  new model-selection or strategy-engine logic must go through
  `ModelRegistry.ranked()`/`best()`-style filtering, not reintroduce an
  existence-only check.
- The `StateManager` persistence contract — `repositoryEvidence` and every
  other field with a working setter must actually get called from wherever
  the corresponding value is computed. Fix #4 exists because that discipline
  broke down once already.
- Role/tool authorization boundaries in `tool-gate.ts` (`TOOL_ROLES`) — a
  v0.2 Workflow Engine must not grant execution-tool access to non-execution
  roles (ARCHITECT, REVIEWER, ALTERNATIVE_REVIEWER, VALIDATOR) without a
  deliberate, separate decision.
- The DevMesh ↔ FreeLLMAPI HTTP-only boundary (Section 4) — no new direct
  filesystem/import-based coupling to FreeLLMAPI internals should be added
  without the same scrutiny applied to item #15.

## 6. Candidate v0.2 Capabilities (Not Yet Implemented)

From the proposed ECC/gstack/CCG-influenced architecture — listed here as
candidates for evaluation, not commitments:

- **Knowledge/Skills layer** (ECC-inspired) — domain-specific engineering
  knowledge (architecture, security, testing, debugging, robotics, AI/ML,
  embedded, DevOps) loaded contextually per mission rather than a single
  generic prompt per role.
- **Workflow Engine** (gstack-inspired) — mission classification into
  distinct workflows (BUILD, DEBUG, REFACTOR, SECURITY, RESEARCH, AUDIT,
  RELEASE) instead of the current fixed ARCHITECT→IMPLEMENTER→REVIEW→
  REPAIR→VALIDATE sequence.
- **Strategy/Model-Orchestration layer** (CCG-inspired) — intent
  classification, strategy selection, and model allocation as an explicit
  layer above the current per-role routing.

**Prerequisite, not yet done:** actually reading ECC, gstack, and CCG source
code — not just their READMEs or the proposal's summary of them — the same
way this v0.1 audit read DevMesh's actual source rather than trusting
descriptions of it.
